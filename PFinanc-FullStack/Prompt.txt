# Build a Self-Hosted Personal & Family Finance Management Application — Phase 1

You are a senior full-stack engineer, backend architect, database architect, product designer, and security engineer.

Your task is to design and implement **Phase 1 of a personal and family finance management application**.

This is primarily a private application for personal/family use. It is not currently intended to be a SaaS product or commercial finance application.

The primary objective is:

> Build a reliable financial ledger and family finance management system that allows multiple family members to manage bank accounts, income, expenses, transfers, and overall household net worth without requiring complicated manual maintenance.

The architecture must be designed so that future phases can add:

* Android React Native application
* SMS transaction ingestion
* Email transaction ingestion
* Automatic transaction classification
* AI-assisted transaction categorization
* Investment portfolio tracking
* Stock and mutual-fund price synchronization
* EPF/PPF/NPS tracking
* Recurring financial events
* Notifications and reminders
* Reconciliation
* Financial analytics
* Advanced financial intelligence

However, **do not implement these future features in Phase 1 unless explicitly required below**.

---

# 1. PRODUCT PHILOSOPHY

The application should follow these principles:

1. Financial data should have a single source of truth.
2. Internal transfers must never be incorrectly counted as income or expenses.
3. Every financial event should be auditable.
4. Data should not be silently modified by automation.
5. The application should be usable by multiple family members.
6. Users should only see financial information they are authorized to see.
7. The database architecture should support future automation.
8. The system should be simple enough for a single developer to maintain.
9. Do not over-engineer with microservices.
10. Prefer correctness and maintainability over unnecessary abstraction.

The application is fundamentally a **financial ledger + account management + household dashboard**.

# 13. TRANSFERS — VERY IMPORTANT

Transfers between accounts must be implemented as a first-class concept.

Example:

```text
Mitesh HDFC
    ↓
₹10,000
    ↓
Father SBI
```

This is NOT:

```text
Mitesh Expense ₹10,000
Father Income ₹10,000
```

It is:

```text
Mitesh account: -₹10,000
Father account: +₹10,000
```

but both sides belong to one transfer event.

Create a dedicated transfer representation.

For example:

```text
transfers
```

with:

```text
id
household_id
source_account_id
destination_account_id
amount
currency
transfer_date
status
description
reference
created_by
created_at
updated_at
```

A transfer should generate two linked ledger effects:

```text
SOURCE
- amount

DESTINATION
+ amount
```

The transfer itself must not appear in:

* Income totals
* Expense totals
* Household spending analytics

It should appear in:

* Account activity
* Transfer history
* Cash-flow movement
* Individual account balance changes

# 15. BALANCE CALCULATION

# 16. DOUBLE-COUNTING PREVENTION

This is a critical requirement.

For:

```text
Mitesh HDFC
→ Father SBI
```

the system must NOT calculate:

```text
Household Expense +₹10,000
```

and must NOT calculate:

```text
Household Income +₹10,000
```

Household net worth should remain unchanged.

Only when Father spends the money should household net worth decrease.

Example:

```text
Initial household net worth:
₹10,00,000

Mitesh transfers ₹10,000 to Father:

Household net worth:
₹10,00,000

Father spends ₹2,000:

Household net worth:
₹9,98,000
```

Write automated tests for this behavior.

# 51. IMPORTANT ACCOUNTING RULES

Implement these rules explicitly and test them.

### Rule 1

Confirmed expense decreases account balance.

### Rule 2

Confirmed income increases account balance.

### Rule 3

Transfer decreases source account.

### Rule 4

Transfer increases destination account.

### Rule 5

Transfer does not count as household income.

### Rule 6

Transfer does not count as household expense.

### Rule 7

Draft transactions do not affect balances.

### Rule 8

Rejected transactions do not affect balances.

### Rule 9

Voided transactions do not affect current balances.

### Rule 10

A transfer must be atomic.

### Rule 11

A user cannot modify another user's private account unless authorized.

### Rule 12
